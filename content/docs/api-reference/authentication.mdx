# Authentication

The Shop API has two authentication schemes.

| Scheme | Headers | Used for |
|--------|---------|----------|
| **API credentials** | `X-API-Key` + `X-API-Secret` | Nearly everything: server-to-server and POS calls |
| **JWT** | `Authorization: Bearer <token>` | The few customer-scoped endpoints, such as `GET /{locale}/shop/auth/me` |

## API credentials

Generate a key/secret pair in the [Partners Portal](https://partners.loyalty.lt) →
**API Credentials**. Pick the environment when you create them: staging credentials only
work against `staging-api.loyalty.lt`, production ones only against `api.loyalty.lt`.

Both headers are required on every request — sending one without the other is a `401`.

```bash
curl -X GET "https://api.loyalty.lt/lt/shop/loyalty-cards" \
  -H "X-API-Key: $LOYALTY_API_KEY" \
  -H "X-API-Secret: $LOYALTY_API_SECRET" \
  -H "Content-Type: application/json"
```

<Warning>
The secret is shown once and must stay on your server. Never ship it in frontend code
or a mobile app bundle.
</Warning>

Check a pair without touching real data:

```bash
curl -X POST "https://api.loyalty.lt/lt/shop/validate-credentials" \
  -H "X-API-Key: $LOYALTY_API_KEY" \
  -H "X-API-Secret: $LOYALTY_API_SECRET"
```

A credential can also be restricted to specific IP addresses. Calls from anywhere else
return `403`.

## QR login

QR login signs a customer in on a screen with no keyboard — a POS terminal or a checkout
page. You show a QR code, they scan it in the Loyalty.lt app, and you receive their JWT.

<Steps>
<Step title="Open a session">
  ```bash
  curl -X POST "https://api.loyalty.lt/lt/shop/auth/qr-login/generate" \
    -H "X-API-Key: $LOYALTY_API_KEY" \
    -H "X-API-Secret: $LOYALTY_API_SECRET" \
    -H "Content-Type: application/json" \
    -d '{"device_name": "Till 3", "shop_id": 1}'
  ```

  The response carries `session_id`, the `qr_code` payload to render, and `expires_at`.
  Sessions last **5 minutes**.
</Step>

<Step title="Render the code and wait on the channel">
  Subscribe to `qr-login.{session_id}` and bind `status_update`. The channel is public —
  the unguessable session ID is the secret — so there is nothing to authorize.

  Full payloads, status values and the connection snippet are in
  [Realtime](/docs/api-reference/realtime). If you cannot hold a WebSocket open, poll
  instead:

  ```bash
  curl -X POST "https://api.loyalty.lt/lt/shop/auth/qr-login/poll/{session_id}" \
    -H "X-API-Key: $LOYALTY_API_KEY" \
    -H "X-API-Secret: $LOYALTY_API_SECRET"
  ```
</Step>

<Step title="Use the token">
  On `status: "authenticated"` the payload carries the customer's `token` and `user`.
  Send the token as `Authorization: Bearer <token>` on customer-scoped endpoints.
</Step>
</Steps>

If the customer does not have the app yet, text them the download link rather than
leaving them stuck at the till:

```bash
curl -X POST "https://api.loyalty.lt/lt/shop/auth/send-app-link" \
  -H "X-API-Key: $LOYALTY_API_KEY" \
  -H "X-API-Secret: $LOYALTY_API_SECRET" \
  -H "Content-Type: application/json" \
  -d '{"phone": "+37060000001", "shop_id": 1}'
```

## Customer JWT

The token from QR login identifies one customer:

```bash
curl -X GET "https://api.loyalty.lt/lt/shop/auth/me" \
  -H "Authorization: Bearer $TOKEN"
```

It is also what signs a private realtime channel — see
[Realtime](/docs/api-reference/realtime).

The Shop API has no password login, refresh or logout endpoint. A token comes from QR
login; when it expires, run QR login again. Partner-account sign-in for the Partners
Portal is a separate flow under `/{locale}/partners/auth/...` and is not part of the
Shop API.

## Errors

| Status | Cause |
|--------|-------|
| `401` | A header missing, wrong key/secret, wrong environment, or an expired credential |
| `403` | IP not allowlisted, or the partner's plan does not include API access |

Both return the standard envelope with a `request_id` — see
[API Overview](/docs/api-reference/overview).
