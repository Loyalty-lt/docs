# Authentication

The Shop API has two authentication schemes.

| Scheme | Headers | Used for |
|--------|---------|----------|
| **API credentials** | `X-API-Key` + `X-API-Secret` | Nearly everything: server-to-server and POS calls |
| **JWT** | `Authorization: Bearer <token>` | The few customer-scoped endpoints, such as `GET /{locale}/shop/auth/me` |

## API credentials

Generate a key/secret pair in the [Partners Portal](https://partners.loyalty.lt) →
**API Credentials**. Pick the environment when you create them: staging credentials
only work against `staging-api.loyalty.lt`, production ones only against
`api.loyalty.lt`.

Send both headers on every request:

```bash
curl -X GET "https://staging-api.loyalty.lt/en/shop/loyalty-cards" \
  -H "X-API-Key: $LOYALTY_API_KEY" \
  -H "X-API-Secret: $LOYALTY_API_SECRET" \
  -H "Content-Type: application/json"
```

<Warning>
The secret is shown once and must stay on your server. Never ship it in frontend code
or a mobile app bundle.
</Warning>

You can check a pair without touching real data:

```bash
curl -X POST "https://staging-api.loyalty.lt/en/shop/validate-credentials" \
  -H "X-API-Key: $LOYALTY_API_KEY" \
  -H "X-API-Secret: $LOYALTY_API_SECRET"
```

A credential can also be restricted to specific IP addresses. Calls from anywhere
else return `403`.

## QR login

QR login is how a customer signs in on a screen that has no keyboard — a POS terminal
or a checkout page. You show a QR code, they scan it in the Loyalty.lt app, and you
get back a JWT for that customer.

<Steps>
<Step title="Generate a session">
  ```bash
  curl -X POST "https://staging-api.loyalty.lt/en/shop/auth/qr-login/generate" \
    -H "X-API-Key: $LOYALTY_API_KEY" \
    -H "X-API-Secret: $LOYALTY_API_SECRET" \
    -H "Content-Type: application/json" \
    -d '{"device_name": "Till 3"}'
  ```

  The response carries a `session_id` and the QR payload to render. Sessions expire
  after 5 minutes.
</Step>

<Step title="Show the QR code and wait">
  Either subscribe to the realtime channel (preferred, below) or poll:

  ```bash
  curl -X POST "https://staging-api.loyalty.lt/en/shop/auth/qr-login/poll/{session_id}" \
    -H "X-API-Key: $LOYALTY_API_KEY" \
    -H "X-API-Secret: $LOYALTY_API_SECRET"
  ```
</Step>

<Step title="Use the token">
  Once the customer confirms in the app, the session returns their JWT. Send it as
  `Authorization: Bearer <token>` on customer-scoped endpoints.
</Step>
</Steps>

If the customer does not have the app yet, text them the download link instead of
leaving them stuck at the till:

```bash
curl -X POST "https://staging-api.loyalty.lt/en/shop/auth/send-app-link" \
  -H "X-API-Key: $LOYALTY_API_KEY" \
  -H "X-API-Secret: $LOYALTY_API_SECRET" \
  -H "Content-Type: application/json" \
  -d '{"phone": "+37060000001"}'
```

### Realtime instead of polling

`GET /{locale}/shop/realtime/config` returns the connection details for Laravel
Reverb, which speaks the Pusher protocol. Do not hardcode the host — read it from
this endpoint.

```javascript
const res = await fetch('https://staging-api.loyalty.lt/en/shop/realtime/config', {
  headers: { 'X-API-Key': apiKey, 'X-API-Secret': apiSecret },
});
const { data: config } = await res.json();

const pusher = new Pusher(config.key, {
  wsHost: config.host,
  wsPort: config.port,
  wssPort: config.port,
  forceTLS: config.scheme === 'https',
  enabledTransports: ['ws', 'wss'],
  cluster: '',        // Reverb has no clusters, but pusher-js requires the option
  disableStats: true,
});

pusher.subscribe(`qr-login.${sessionId}`).bind('status_update', (payload) => {
  if (payload.status === 'authenticated') {
    console.log(payload.user, payload.token);
  }
});
```

<Note>
The `qr-login.{session_id}` channel is public — the unguessable session ID is the
secret — so there is no channel authorization step.
</Note>

## Customer JWT

The token from QR login identifies one customer:

```bash
curl -X GET "https://staging-api.loyalty.lt/en/shop/auth/me" \
  -H "Authorization: Bearer $TOKEN"
```

The Shop API has no password login, refresh or logout endpoint. A token comes from QR
login; when it expires, run QR login again. Partner-account sign-in for the Partners
Portal is a separate flow under `/{locale}/partners/auth/...` and is not part of the
Shop API.

## Errors

| Status | Cause |
|--------|-------|
| `401` | Header missing, wrong key/secret, wrong environment, or expired credential |
| `403` | IP not allowlisted, or the partner's plan does not include API access |

Both return the standard envelope with a `request_id` — quote it when contacting
support. See [API Overview](/docs/api-reference/overview#response-format).
