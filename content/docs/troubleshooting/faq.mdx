# FAQ

## Getting started

<AccordionGroup>

<Accordion title="How do I start?">
1. Create an account at [partners.loyalty.lt](https://partners.loyalty.lt).
2. Generate **staging** API credentials under **API Credentials**.
3. Install an [SDK](/docs/sdk/overview), or call the REST API directly.
4. Build against staging, then create production credentials and change the base URL.
</Accordion>

<Accordion title="Which languages have an SDK?">
- **JavaScript / TypeScript** — `@loyaltylt/sdk`, Node.js 16+, with React components
- **PHP** — `loyaltylt/sdk`, PHP 8.1+
- **Python** — `loyaltylt-sdk`, Python 3.8+

Anything else can call the REST API over HTTPS.
</Accordion>

<Accordion title="What is in the API?">
The **Shop API** (`/{locale}/shop/...`) is what stores and POS systems use: loyalty
cards, transactions and points, coupons, games, offers, XML product import, QR login
and QR card scan.

The **SMS API** (`/{locale}/sms/...`) sends transactional SMS with delivery receipts
and consent records.

Both use the same credentials and the same response envelope.
</Accordion>

</AccordionGroup>

## Authentication

<AccordionGroup>

<Accordion title="Why am I getting 401?">
In order of likelihood:

1. Staging credentials against `api.loyalty.lt`, or production credentials against
   `staging-api.loyalty.lt`. They are not interchangeable.
2. Only one of the two headers sent — both `X-API-Key` and `X-API-Secret` are required.
3. The credential was revoked or expired in the Partners Portal.

Check a pair with `POST /{locale}/shop/validate-credentials`.
</Accordion>

<Accordion title="Why am I getting 403 with valid credentials?">
Either the credential is restricted to a set of IP addresses and your server is not
on it, or the partner's plan does not include API access. Both are settings in the
Partners Portal.
</Accordion>

<Accordion title="The customer cannot scan the QR code">
Show `manual_code` beside it. Both QR endpoints return one — nine digits formatted
`XXX-XXX-XXX` — and the Loyalty.lt app has an entry sheet for typing it. It opens the
same session the QR would have, so everything downstream is identical.
</Accordion>

<Accordion title="How does a customer sign in?">
Through QR login: you show a QR code, they scan it in the Loyalty.lt app, and you get
a JWT. There is no password login, refresh or logout endpoint on the Shop API — when
a token expires, run QR login again. See
[Authentication](/docs/api-reference/authentication).
</Accordion>

</AccordionGroup>

## Points and transactions

<AccordionGroup>

<Accordion title="How do I award points for a purchase?">
One call:

```bash
POST /{locale}/shop/transactions/create
{
  "user_email": "customer@example.com",
  "order_id": "ORD-2024-001",
  "order_total": 25.50,
  "currency": "EUR",
  "shop_id": 1
}
```

`order_id` is required, and so is one of `user_id` / `user_email`. Points are
calculated from `order_total` using the partner's rules; pass `points` to set the
number yourself.
</Accordion>

<Accordion title="A customer returned an order — how do I take the points back?">
Send the same `order_id` again with `"type": "cancellation"` or `"refund"`. Earned
points are reversed and any points they spent are returned.
</Accordion>

<Accordion title="How do I stop points being spent twice during checkout?">
Reserve them: `POST /{locale}/shop/points/reserve` with the `order_id`, then either
confirm by calling `transactions/create` with that same `order_id`, or free them with
`points/release` if checkout is abandoned.
</Accordion>

<Accordion title="Why is my request returning 422?">
A 422 carries `code: 1100` and an `errors` object keyed by field name — read it, it
names the field and the rule. The most common causes are a missing `order_id`, or
neither `user_id` nor `user_email`.
</Accordion>

</AccordionGroup>

## Coupons and games

<AccordionGroup>

<Accordion title="What is the right order for redeeming a coupon?">
`coupons/verify` before showing a discount → `coupons/pending` while the sale is open
→ `coupons/redeem` once payment succeeds. If the sale falls through, call
`coupons/cancel-pending` so the customer keeps the coupon. Redemption is final.
</Accordion>

<Accordion title="Do I have to issue the stamp-card reward myself?">
No. When a stamp card fills up, the reward is issued automatically. `games/{id}/complete`
and `games/{id}/restart` exist for closing and restarting a round by hand.
</Accordion>

</AccordionGroup>

## Operations

<AccordionGroup>

<Accordion title="My WebSocket will not connect — what do I check?">
Read `host`, `port` and `scheme` from `GET /{locale}/shop/realtime/config` rather than
hardcoding them. For a **private** channel you also need `authEndpoint` pointing at
`POST /{locale}/broadcasting/auth` with a customer JWT — a `403` there means the channel
does not belong to that customer. If you send a client event and get `pusher:error`
code `4009`, you are not subscribed to the channel you are sending on. See
[Realtime](/docs/api-reference/realtime).
</Accordion>

<Accordion title="What should I retry?">
`429` and `5xx`, with exponential backoff. Never retry other `4xx` — they will fail
the same way. The SDKs already do this for you.
</Accordion>

<Accordion title="Is there a rate limit?">
Yes; exceeding it returns `429`. Back off and retry rather than tightening a loop.
Contact support if you need a higher limit for a bulk job.
</Accordion>

<Accordion title="404 card not found on staging">
Production cards do not exist in staging, and the demo card numbers change on every
weekly refresh. Look a card up by the customer's email or phone rather than by a number
you saved.
</Accordion>

<Accordion title="When does staging reset?">
Sunday morning: the database is cleared at 04:00 EET, your catalogue is re-copied from
production at 05:00, and the demo customers and their cards are recreated at 06:00. Your
API credentials survive; the demo card IDs change. See
[Staging](/docs/api-reference/staging).
</Accordion>

<Accordion title="Where do I get shop_id?">
`GET /{locale}/shop/shops`, or `sdk.getShops()`. Many calls are scoped to a shop.
</Accordion>

</AccordionGroup>

## Still stuck?

Email [developers@loyalty.lt](mailto:developers@loyalty.lt) with your partner ID, the
endpoint, and the `request_id` from the response — every response carries one,
successes included, and it lets support find the exact request.
